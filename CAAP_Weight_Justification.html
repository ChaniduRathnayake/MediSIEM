Clinical Alert Score · Weight Justification

Why these weights?
Why not equal weighting?

Each CAS weight encodes a clinical safety principle. Equal weights (0.20 each) would treat a hospital shift the same as a device type — that is clinically wrong.

Three-Method Justification
Method 1 — AHP Analytic Hierarchy Process (Saaty, 1980)

Pairwise comparisons produce a mathematically consistent weight vector. A Consistency Ratio < 0.10 proves the judgements are logically coherent — turning intuition into an academically defensible decision.

AHP-derived weights ≈ current weights → validates that current assignment is internally consistent · CR = CI/RI, RI=1.12 for n=5 · Target CR < 0.10

Method 2 — Standards Official Framework Alignment

CC → IEC 80001-1 §4.3 — "Patient safety is the primary risk criterion for medical IT networks." Highest weight directly follows this mandate.


TR / AE → CVSS v3.1 / NVD — CVSS exploitability and impact provide the technical grounding for attack severity.


TS → NIST SP 800-30 Rev 1 — Temporal anomaly factors are included in likelihood assessment. Equal weight to TR reflects that neither signal alone is sufficient.


TC → IEC 80001-1 §5.4 — Operational environment risk. Staff availability modifies patient safety risk without overriding clinical signals.

Method 3 — Sensitivity Perturbation Robustness Test

Perturb each weight by ±0.05. If the action tier (Immediate / Investigate / Monitor) for life-critical devices does not change, the weights are robust — not arbitrary.


ICU Ventilator + DoS_TCP + Night shift
Baseline (current) CAS 10.0 → Immediate ✓
CC = 0.35 (+0.05) CAS 10.0 → Immediate ✓
CC = 0.25 (−0.05) CAS 9.5 → Immediate ✓
TR = 0.30 (+0.05) CAS 10.0 → Immediate ✓

Action tier remains Immediate across all perturbations for critical devices. Weights are robust.

Method 4 — Extension Contextual Re-weighting (scenario-adaptive profiles)

Methods 1–3 establish that one fixed weight vector is internally consistent (AHP, CR<0.10), standards-grounded, and robust to small perturbation. They do not establish that a single global vector is optimal across every deployment context — an ICU's alert stream and an administrative ward's are not drawn from the same risk distribution. CAAP now supports named, per-scenario weight profiles (ai_server/src/cas_config.py's SCENARIO_WEIGHT_PROFILES), auto-selected from the alerting device's department and editable per-deployment from Settings → CAS Weights, with every profile validated to sum to 1.00 and every dimension's TR/CC/TS/AE/TC value computed identically regardless of which profile scores it — only the relative weighting changes.

This is additive, not a replacement: every profile ships seeded as an identical copy of the Method 1–3 default above until a deployment's own AHP-style pairwise comparison justifies diverging from it — the same rigor this page already applies to the single default vector should be applied per-scenario before its weights are allowed to differ in production, not asserted here. ai_server/src/hospital_scenarios.py's build_static_vs_adaptive_table() runs the identical ARA/MTCAI/FPR evaluation this page's own CAAP-vs-CVSS comparison uses, but of static-default-weights vs. scenario-adaptive-weights on the same alert stream — the mechanism to measure whether contextual re-weighting is worth adopting for a given deployment, once its profiles have been deliberately tuned.

Why not equal weights (0.20 each)?
Equal weights — what goes wrong

With 0.20 each: an attack on an Admin PC at night (TC=5, tr=4, ts=3, ae=2, cc=0.5) scores CAS ≈ 5.8 → Investigate.

An attack on an ICU Ventilator during day shift (CC=5, tr=4, ts=3, ae=5, tc=1) scores CAS ≈ 7.2 → Investigate.

Same tier. A SOC analyst cannot tell which one may kill a patient.

Calibrated weights — the correct behaviour

With CAAP weights: the ICU Ventilator attack scores CAS ≈ 8.8 → Immediate.

The Admin PC attack scores CAS ≈ 5.2 → Investigate.

CC's higher weight (0.30 vs 0.20) provides the separation. This separation is the core academic contribution of CAAP over raw CVSS.

Viva Q&A Reference
Q: Why CC=0.30 not 0.25?
IEC 80001-1 §4.3 makes patient safety the primary criterion. CC is the only dimension that directly encodes patient harm potential — it must dominate. Equal weights would fail to distinguish ICU device attacks from office PC attacks.
Q: Why TR = TS = 0.25?
Neither ML classification confidence alone nor anomaly magnitude alone is sufficient. A high-confidence classification of a non-anomalous event may be normal. An anomaly without classification context is ambiguous. Equal weight forces both signals to agree before escalating.
Q: Why AE only 0.10?
Attack type is already partially captured by TR (the RF model identifies the label). AE provides supplementary CVE context — it refines the score without duplicating the TR signal. Supporting weight is appropriate.
Q: Why TC only 0.10?
Hospital shift affects response time, not the attack itself. A night shift attack on an Admin PC should not outrank a day shift attack on an ICU ventilator. TC modifies without overriding — supporting weight is the correct choice.
Q: What if the weights are wrong?
The sensitivity analysis (±0.05 perturbation across all 5 dimensions) shows that the action tier for life-critical device attacks remains Immediate in all tested scenarios. The weights are robust to small errors.
Q: How do these compare to CVSS weights?
CVSS has no clinical dimension whatsoever — it weights attack vector, complexity, and CIA impact equally across all device types. CAAP adds CC (device type), TS (anomaly time pressure), and TC (staff availability) — dimensions that are clinically essential but absent in CVSS.
Q: Isn't a fixed weight vector a limitation — shouldn't weighting adapt to context?
It can, and now does (Method 4, previous page): named scenario profiles (ICU/Critical Care, General Ward/Admin, Hospital-Wide Mixed) resolved from the alerting device's department, admin-editable at runtime with no redeploy. Every profile still ships as an exact copy of the Method 1–3 default until deliberately tuned, and hospital_scenarios.py can measure whether a tuned profile actually improves alert-ranking accuracy over the static default before it's trusted in production — the fixed vector's defensibility (AHP, CR<0.10, standards mapping) isn't lost, it's the baseline every scenario profile is validated against.
