# Alert Schema (Enriched Alert)

> **Version:** 1.0
> **Last updated:** 2026-05-03
> **Owner:** W.D.S Jayasinghe (decision engine)
> **Producer:** Enrichment module (teammate; stub implementation in this repo)
> **Consumer:** Decision engine, audit log, SOC dashboard

---

## Purpose

This schema defines the **enriched alert** — the contract between the
enrichment module and every downstream component (decision engine,
dashboard, audit log, playbooks).

A raw SIEM alert is enriched with **clinical context** by the enrichment
module before it reaches the decision engine. The decision engine relies
on this enrichment to make Security-vs-Life tiered response decisions.

This schema is the most important interface in the project: anything not
in the schema is invisible to the engine.

---

## Top-level structure

The alert is a JSON object with five top-level blocks plus identification
fields. **The structure (these five blocks) is locked. Fields *inside*
the blocks are flexible** and may evolve as the enrichment module matures.

```json
{
  "alert_id":         "...",
  "timestamp":        "...",
  "source":           { ... },
  "threat":           { ... },
  "asset":            { ... },
  "clinical_context": { ... },
  "enrichment_meta":  { ... }
}
```

| Block | Purpose | Producer |
|-------|---------|----------|
| `source` | Which SIEM / rule produced the raw alert | SIEM (Wazuh) |
| `threat` | What kind of threat, how severe | SIEM (Wazuh) |
| `asset` | Which device/system is affected | SIEM + enrichment |
| `clinical_context` | Clinical criticality of the asset | **Enrichment module** |
| `enrichment_meta` | Provenance of the enrichment | Enrichment module |

## Identification fields

| Field | Type | Required | Description | Example |
|-------|------|----------|-------------|---------|
| `alert_id` | string | yes | Globally unique ID for this alert. Used as the audit log key. | `"alert-2026-05-03-0001"` |
| `timestamp` | string (ISO 8601, UTC) | yes | When the alert was generated by the SIEM. | `"2026-05-03T18:30:00Z"` |

## `source` block

Where the raw alert came from.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `siem` | string | yes | SIEM platform name. PP1: always `"wazuh"`. |
| `rule_id` | string | yes | The SIEM rule ID that fired. |
| `rule_description` | string | no | Human-readable rule description. |
| `rule_level` | integer (0–15) | no | SIEM-native severity level (e.g. Wazuh 0–15). |

**Example:**

```json
"source": {
  "siem": "wazuh",
  "rule_id": "92052",
  "rule_description": "Multiple authentication failures from same source IP",
  "rule_level": 10
}
```

## `threat` block

What kind of threat this is and how severe.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `category` | string | no | Threat category (e.g. `"brute_force"`, `"ransomware"`, `"active_exploitation"`, `"data_exfiltration"`, `"lateral_movement"`). |
| `technical_severity` | enum: `"low"` / `"medium"` / `"high"` / `"critical"` | yes (one of `technical_severity` or `cvss_score`, unless `cas_score` is present) | Categorical severity. |
| `cvss_score` | number (0.0–10.0) | yes (one of `technical_severity` or `cvss_score`, unless `cas_score` is present) | CVSS v3 base score. |
| `cas_score` | number (0.0–10.0) | no | MediSIEM CAAP's blended severity score — same 0–10 scale as `cvss_score`, NOT 0–1. Folds in technical risk, attack exploitability, and time context on top of raw attack severity. **When present, this is the authoritative severity signal** — the engine reads it instead of `cvss_score` (see *Decision logic* below). |
| `cas_breakdown` | object | no | Display-only sub-scores behind `cas_score` (`TR`/`CC`/`TS`/`AE`/`TC`). The engine never reads this. |
| `indicators` | object | no | Free-form indicators of compromise (IPs, ports, hashes, etc.). |

**Severity mapping (decision engine convention):**

| `cvss_score` | `technical_severity` |
|--------------|----------------------|
| 0.0–3.9 | `low` |
| 4.0–6.9 | `medium` |
| 7.0–8.9 | `high` |
| 9.0–10.0 | `critical` |

The decision engine prefers `cas_score` if present; otherwise `cvss_score`;
otherwise falls back to `technical_severity`.

**Extreme threat (engine-internal classification):**

The engine treats a threat as **extreme** when **either** of the following
is true:

- The numeric severity signal clears 9.0 — `cas_score` when present,
  otherwise `cvss_score`. (`cas_score` fully replaces `cvss_score` for this
  check the moment a producer supplies one; the two are never combined.) OR
- `category` is one of: `"ransomware"`, `"active_exploitation"` — this
  check is independent of which numeric signal was used, or whether either
  was available at all. A known-dangerous category always escalates, even
  if the numeric score itself landed under threshold.

Extreme threats are the only signal that escalates a protected asset
(`clinical_support` or `life_critical`) from Tier 2 (Monitored Mode) to
Tier 3 (Clinician Approval). See *Decision matrix* below.

**Example:**

```json
"threat": {
  "category": "brute_force",
  "technical_severity": "high",
  "cvss_score": 7.5,
  "indicators": {
    "source_ip": "192.168.1.42",
    "destination_port": 22
  }
}
```

## `asset` block

Which device or system the alert is about.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `asset_id` | string | yes | Stable internal asset ID. Joins to the asset registry. |
| `hostname` | string | no | DNS hostname. |
| `ip_address` | string | no | IP address at time of alert. |
| `asset_type` | enum: `"medical_device"` / `"workstation"` / `"server"` / `"network"` / `"other"` | no | Broad asset class. |
| `device_category` | string | no | Specific device class (e.g. `"ventilator"`, `"infusion_pump"`, `"radiation_therapy"`, `"laptop"`). |
| `department` | string | no | Hospital department (`"ICU"`, `"ER"`, `"oncology"`, `"administration"`, etc.). |
| `patient_facing` | boolean | no | Does this asset interact directly with patient care? |

**Example:**

```json
"asset": {
  "asset_id": "ICU-VENT-003",
  "hostname": "icu-ventilator-03.hospital.local",
  "ip_address": "10.0.5.23",
  "asset_type": "medical_device",
  "device_category": "ventilator",
  "department": "ICU",
  "patient_facing": true
}
```

## `clinical_context` block — *the heart of the schema*

The enrichment module's contribution. This is what makes the framework
**life-critical-aware**.

### Authoritative field (engine reads this)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `criticality_score` | integer (1–10) | yes | Numeric weight of the asset's clinical importance. Higher = more critical. **The single signal the decision engine reads to determine asset criticality.** |

> **Note on field naming.** The enrichment module's internal column for
> this value is named `cc_score` (clinical-criticality score). It is
> mapped to `criticality_score` at ingest into the engine. Both names
> refer to the same value on the same 1–10 scale; the rename is purely
> for self-describing schema field names and producer-agnostic naming.
> Coordinated with the enrichment teammate.

### Display-only metadata fields (engine ignores; surfaced on dashboard)

The following fields provide context for SOC analysts and clinical staff
viewing the dashboard or audit log. **They do not influence the engine's
tier decision.** They are produced by the enrichment module.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `patient_dependency` | string | no | Categorical description of how dependent patient care is on this asset. Vocabulary defined by enrichment module. **One of the two inputs from which the enrichment module derives `criticality_score`.** |
| `time_sensitivity` | number | no | Numeric measure of how time-sensitive this asset is to disruption. Scale defined by enrichment module. **One of the two inputs from which the enrichment module derives `criticality_score`.** |
| `shift` | string | no | Hospital shift in effect at alert time (e.g. `"day"`, `"evening"`, `"night"`). Useful for SOC context (staffing levels, escalation paths). |

> **Why does the engine ignore these?** The enrichment module
> consolidates `patient_dependency` and `time_sensitivity` into a single
> `criticality_score` (1–10). Reading the raw inputs again in the engine
> would either duplicate the enrichment logic or risk diverging from it.
> Single signal in, single decision out — clean separation of concerns.
> The raw inputs are still surfaced on the dashboard so SOC analysts see
> the full clinical picture.

### Criticality bands (derived by engine)

The engine maps `criticality_score` to a categorical band as follows:

| `criticality_score` | derived band |
|---------------------|--------------|
| 1–4 | `non_critical` |
| 5–7 | `clinical_support` |
| 8–10 | `life_critical` |

The threshold at `5` is set by the enrichment module: `cc_score < 5`
indicates a non-critical asset; `cc_score >= 5` indicates a clinically
relevant asset that must be protected from disruptive automated
containment.

The engine emits the derived band name in its decision response, audit
log, and dashboard payload. It is **not** an input field on this schema.

### Fail-safe rule (critical)

**If `criticality_score` is missing, invalid, or out of range, the
decision engine treats the asset as `life_critical` (band) with the
maximum score (10) for tier-decision purposes.** This is a deliberate
safety default: when in doubt, never disrupt patient care.

**Example:**

```json
"clinical_context": {
  "criticality_score": 10,
  "patient_dependency": "life_sustaining",
  "time_sensitivity": 4.8,
  "shift": "night"
}
```

## Decision logic (how the engine consumes the schema)

The engine reads only `criticality_score` (from `clinical_context`),
`cvss_score` / `technical_severity` (from `threat`), and `category`
(from `threat`). It produces a tier decision and an action.

### Action vocabulary

| Action | Tier | When |
|--------|------|------|
| `log_only` | Tier 1 | Non-critical asset, low-severity threat. Note and move on. |
| `block_port` | Tier 1 | Non-critical asset, medium-severity threat. Narrow disruptive containment. |
| `isolate_host` | Tier 1 | Non-critical asset, high or extreme threat. Full disruptive containment. |
| `monitored_mode` | Tier 2 | Protected asset, non-extreme threat. Non-disruptive observation (see below). |
| `await_clinician_approval` | Tier 3 | Protected asset, extreme threat. Human-in-the-loop required (see below). |

### Decision matrix

Asset criticality (rows) gates whether the asset is treated as protected
at all. Threat severity (columns) drives the Tier 1 action choice and the
Tier 2 / Tier 3 split for protected assets.

| `criticality_score` (band) | low CVSS (<4) | medium (4–6.9) | high (7–8.9) | extreme (≥9 OR ransomware / active_exploitation) |
|----------------------------|---------------|----------------|--------------|--------------------------------------------------|
| 1–4 (`non_critical`)       | **Tier 1** `log_only`     | **Tier 1** `block_port`   | **Tier 1** `isolate_host` | **Tier 1** `isolate_host` |
| 5–7 (`clinical_support`)   | Tier 2 `monitored_mode`   | Tier 2 `monitored_mode`   | Tier 2 `monitored_mode`   | **Tier 3** `await_clinician_approval` |
| 8–10 (`life_critical`)     | Tier 2 `monitored_mode`   | Tier 2 `monitored_mode`   | Tier 2 `monitored_mode`   | **Tier 3** `await_clinician_approval` |

**Pseudocode:**

```
IF criticality_score < 5:
    pick action by CVSS band:
        cvss < 4   → Tier 1, log_only
        cvss < 7   → Tier 1, block_port
        else       → Tier 1, isolate_host
ELIF threat is extreme (cvss_score >= 9 OR category in {ransomware, active_exploitation}):
    → Tier 3, await_clinician_approval
ELSE:
    → Tier 2, monitored_mode
```

Both `clinical_support` (5–7) and `life_critical` (8–10) follow the
**same** escalation path. The band distinction exists for dashboard
display and audit-log clarity, not for tier logic.

### Monitored Mode — what it actually means

Monitored Mode is the central differentiator of this framework from
traditional SOAR platforms. It is **not** simply "increased polling
frequency." It is a composite three-part response, executed by the
Shuffle playbook when the engine emits `monitored_mode`:

1. **Deep Telemetry Collection.** Increase log verbosity on the affected
   asset to capture every network packet and system call. This produces
   high-fidelity forensic data for SOC investigators.
2. **Shadow Auditing.** Real-time behavioural comparison of the asset
   against a "known good" clinical baseline. Deviations are flagged for
   the SOC even if they would not normally trigger a SIEM rule.
3. **Zero Interference.** No traffic is blocked. No configurations are
   locked. The device operates at 100% native functionality. Patient
   care is never disrupted by this response.

Monitored Mode is what the framework substitutes for `isolate_host` when
the asset is clinically protected. The engine emits the decision; the
Shuffle playbook executes the three components above.

### Tier 3 — two-phase flow

Tier 3 is **not** a single decision. It is an escalation that pauses for
human input, then resolves into one of two final outcomes. **Throughout
the entire Tier 3 flow — from the moment the engine fires until the
clinician responds — the asset is in Monitored Mode.** There is no
unprotected gap.

**Phase A — Engine + immediate playbook (deterministic, milliseconds):**
The engine emits `tier=3`, `action=await_clinician_approval`, and
`proposed_action_if_approved="isolate_host"`. Two things then happen
in parallel inside the Shuffle playbook:

1. **Monitored Mode is applied to the asset immediately** (deep telemetry +
   shadow auditing + zero interference). This is non-negotiable and not
   contingent on the clinician's response.
2. The clinician approval request is dispatched (PP1: placeholder; PP2:
   full approval UI).

The decision is written to the audit log.

**Phase B — Clinician decision (human-in-the-loop, seconds to minutes):**
The clinician reviews and responds.

| Clinician decision | Final action | What happens |
|--------------------|--------------|--------------|
| **Approve** | `isolate_host` | Asset escalates from Monitored Mode → full host isolation. The clinician has weighed the cyber risk against patient impact and authorised disruption. |
| **Deny** | (stay in `monitored_mode`) | No state change required. The asset has been in Monitored Mode since Phase A; it stays there. Per FR-06, non-disruptive containment is maintained. |

The engine itself never executes Phase B logic. The Shuffle clinician
workflow calls back into the engine's audit log to record the final
outcome alongside the original Tier 3 decision, preserving the full
decision chain for accountability (NFR-01).

> **Why immediate Monitored Mode matters.** If a Tier 3 alert fires (an
> extreme threat on a clinically protected asset) and the playbook merely
> waited for the clinician without containing anything, the asset would
> be unprotected during the entire human-decision window — potentially
> minutes. By applying Monitored Mode immediately, the framework gets the
> best of both worlds: forensic visibility from the moment the threat is
> detected, and the option to escalate to full isolation if and only if
> a clinician authorises it.

## Failure modes

| Missing / invalid field | Engine behaviour |
|-------------------------|------------------|
| `alert_id` | **Reject** the alert (cannot be audited). |
| `timestamp` | Substitute current UTC time, log a warning. |
| `source.siem` | Default to `"unknown"`. |
| `threat.cvss_score` AND `threat.technical_severity` | **Treat as `critical` severity** (cautious). |
| `asset.asset_id` | **Reject** the alert (cannot be tracked). |
| `clinical_context.criticality_score` | **Treat as `life_critical` / score 10** (cautious default). See *Fail-safe rule*. |
| `enrichment_meta` (entire block) | Log a warning; proceed normally. |

## Versioning

This schema is **v1.0**. The major bump from v0.1 reflects two breaking
changes:

- `criticality_score` range changed from 0–100 → 1–10 to match the
  enrichment module's native output (`cc_score`).
- The middle band was renamed from `time_sensitive` → `clinical_support`
  to disambiguate from the new `time_sensitivity` metadata field.

Removed in v1.0 (no producer was filling these): `criticality` (now
derived by the engine from `criticality_score`), `criticality_rationale`,
`currently_in_use`, `fallback_available`.

Added in v1.0 (display-only, from enrichment module): `patient_dependency`,
`time_sensitivity`, `shift`.

Schema evolution rules:

- **Adding** new optional fields → no version bump.
- **Adding** new required fields → minor bump (1.0 → 1.1).
- **Removing or renaming** fields → major bump (1.0 → 2.0); all consumers
  must update.

The current version is recorded in each alert via
`enrichment_meta.enricher_version` (which embeds the schema version).

## Full example

A complete, valid Tier 2 alert:

```json
{
  "alert_id": "alert-2026-05-03-0042",
  "timestamp": "2026-05-03T18:30:00Z",
  "source": {
    "siem": "wazuh",
    "rule_id": "92052",
    "rule_description": "Multiple authentication failures from same source IP",
    "rule_level": 10
  },
  "threat": {
    "category": "brute_force",
    "technical_severity": "high",
    "cvss_score": 7.5,
    "indicators": {
      "source_ip": "192.168.1.42",
      "destination_port": 22
    }
  },
  "asset": {
    "asset_id": "ICU-VENT-003",
    "hostname": "icu-ventilator-03.hospital.local",
    "ip_address": "10.0.5.23",
    "asset_type": "medical_device",
    "device_category": "ventilator",
    "department": "ICU",
    "patient_facing": true
  },
  "clinical_context": {
    "criticality_score": 10,
    "patient_dependency": "life_sustaining",
    "time_sensitivity": 4.8,
    "shift": "night"
  },
  "enrichment_meta": {
    "enriched_at": "2026-05-03T18:30:01Z",
    "enricher_version": "stub-1.0.0",
    "confidence": 1.0
  }
}
```

This alert is classified by the engine as **Tier 2 → `monitored_mode`**:
asset is `life_critical` (score 10 → 8–10 band), threat is `high` but
not extreme (CVSS 7.5 < 9, category `brute_force` is not extreme).
